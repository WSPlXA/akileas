Chapter II

Stack & Architecture

Akileas is built as a strictly layered native application: Rust 2024 and GPUI below, five one-way-dependent layers above, and a hot path measured in microseconds between a keystroke and the first refreshed frame.

2.1 Layered Architecture

The site enforces a single-direction, inward-facing dependency hierarchy. Each layer is aware only of the layer directly beneath it, and no dependency ever points back upward.

  • app/ — the top-level state machine, multi-window sessions, command routing and keybindings.
  • ui/ — GPUI view components, the virtualised render pipeline and appearance themes.
  • render/ + text/ — Ratex formulas, Rusty-Mermaid vectors and an 8MB glyph layout cache.
  • markdown/ + editor/ — Tree-sitter incremental parsing, Ropey buffers and the logarithmic HeightMap.
  • storage/ + agent/ — the SaveTicket ordering lock, atomic writes, the local time machine and Agent sniffing.

The dependency direction runs one way only, from the top down.

2.2 Core Technology Choices

Eight choices define the runtime envelope of the editor.

  • Programming language: Rust 2024 Edition. Zero-cost abstractions and a strong type system rule out data races, and compile-time memory management replaces a runtime GC.
  • UI and graphics engine: GPUI (built by the Zed team). A fully GPU-driven rendering pipeline (native Metal on macOS; DirectX 12 / Vulkan on Windows and Linux), with support for 120Hz/144Hz ultra-high refresh rates and subpixel font rendering.
  • Memory allocator: mimalloc (Microsoft). It replaces the system default malloc, is tuned for small objects and multi-threaded workloads, and eliminates heap fragmentation and jitter.
  • Text data structure: Ropey. A B-Tree-based immutable rope supporting O(log N) insertion and deletion plus copy-free slicing of very large texts.
  • Incremental syntax analysis: Tree-sitter (tree-sitter-md). A two-tier architecture (a block-level syntax tree and a line-level inline syntax tree) performs local, "surgical" incremental pruning over byte ranges.
  • TeX box-model typesetting: Ratex. A pure-Rust implementation of macro-package parsing and Knuth-TeX box-model solving, with no dependency on any JavaScript / Node / browser runtime.
  • Vector diagram compiler: Rusty-Mermaid. Pure Rust compiles Mermaid DSL into immutable GPU vector primitives (paths, polygons, Bézier curves), with a built-in 360x240 locally shaded magnifier.
  • Publication-grade typesetting output: Typst 0.15. A modern typesetting framework that converts the Markdown AST into Typst format and emits high-fidelity vector PDF directly. 
markdown/   Tree-sitter (tree-sitter-md) + Ropey
        editor/     DocumentHeightMap, RenderLineStore, SyntaxIndex
        storage/    SaveTicket, RecoveryJournal, LocalHistoryStore

Crate names, API names and version numbers are reproduced exactly as the project declares them.

2.3 Heterogeneous Compute & Thread Model

The design philosophy is that heterogeneous hardware should each do its own job: compute-intensive and branch-intensive work is divided strictly, rather than blindly porting everything to the GPU or piling all logic onto the main thread.

The wiring is therefore short and explicit: a TextBuffer edit dispatches a parse to Tree-sitter incremental parsing; DocumentAst / SyntaxIndex derivation feeds Ratex and Rusty-Mermaid; Ratex and Rusty-Mermaid hand results back to physical-line projection through a lock-free Arc swap; and the GPU pipeline is connected sequentially inside itself.

NOTE

Nothing on the GPU lane ever blocks the UI lane: the main thread only ever submits a minimal dirty rectangle, while rasterisation, tessellation and shading stay on the hardware pipeline.

2.4 The Dual-Stage Hot Path

To eliminate input stutter in large documents at the root, a text change is decoupled into two stages: an immediate provisional projection on the UI thread, and an authoritative asynchronous parse on a worker pool.

Stage 1: immediate pending raw-line projection (~0.019 ms)

Only the affected raw physical lines are reprojected. The instantaneous output is an unstyled render line that still preserves the cursor and IME anchor, after which the UI submits the minimal dirty-rect scene to the GPU presentation pipeline. The first screen frame therefore shows the moved cursor and the new character with zero perceived latency.

Stage 2: authoritative background async incremental parse (~0.137 ms)

A parse task is dispatched to the worker thread pool carrying document_epoch and generation. The worker reads Rope chunks as a stream and corrects the parse incrementally; the Tree-sitter authority then yields a MarkdownSnapshot, a RenderLineStore and a SyntaxIndex, which the worker submits back to the UI.

Atomic Arc swap takes effect

  1. If the current generation matches, the RenderLineStore is replaced atomically (a shallow Arc clone), and syntax highlighting and rich-text decorations update smoothly.
  2. If the user has already typed new content and the generation is stale, the outdated snapshot is discarded and the editor keeps waiting for the newest generation, which prevents rollback.

IMPORTANT

Generation matching is what makes the two stages safe to run concurrently. A stale snapshot can never overwrite newer text: it is dropped rather than rendered.

2.5 Two-Tier Tree-sitter Parsing over Zero-Copy Rope Chunks

A conventional editor usually hands the document to its parser through a to_string() call, which allocates tens of megabytes of contiguous memory and triggers violent allocation churn and GC pressure. Akileas takes a different route.

  1. Streaming reads straight from Rope chunks. Through a custom streaming reader, Tree-sitter reads the non-contiguous memory pages inside Ropey's chunks directly, with zero memory copying.
  2. Two-level syntax-tree isolation. The block-level syntax tree (Block Tree) only delimits paragraphs, headings, code blocks, block quotes and list boundaries; the line-level syntax tree (Inline Tree) is attached on demand to the blocks that changed. When body characters are edited the block structure stays untouched, so only the affected line is re-parsed for inline syntax while the surrounding 99,999 lines reuse their existing tree nodes in full.
TreeScopeBehaviour on edit
Block Tree (block level) Paragraphs, headings, code blocks, block quotes and list boundaries Remains unchanged while body characters change
Inline Tree (line level) Inline syntax, mounted on demand on changed blocks Only the affected line is re-parsed

TIP

Zero-copy input plus two-tier isolation is what keeps parse cost proportional to the edit rather than to the size of the document.

2.6 Three Decoupled Rich-Text Pipelines

Three mutually isolated rich-text rendering pipelines each carry their own debounce policy, generation validation and cache-eviction strategy.

Ratex LaTeX pipeline

Triggered when formula ranges change: 700ms keyboard debounce, a 32MB box-model LRU cache, and direct GPUI DisplayList output.

Rusty-Mermaid vector pipeline

Triggered by a code block or viewport scroll: viewport clip-window binding, a 32MB geometry path topology cache, and support for the box/ syntax plus the magnifier.

Adaptive table layout pipeline

Triggered when table content is tweaked: hardware-vector memchr splitting and dynamic width computation based on Unicode display units.

2.7 DocumentHeightMap: Logarithmic Virtualisation

In a hundred-thousand-line document, accumulating total height linearly turns any viewport scroll or scrollbar drag into a catastrophic computational bottleneck. Akileas instead implements DocumentHeightMap, a logarithmic height tree.

  • Prefix-sum height accumulation tree. Cumulative height indices are built per block, so editing line 500 updates only the height delta of the local block instead of walking the whole document.
  • O(log N) binary-search lookup. Dragging the scrollbar to the 85% position resolves through binary search directly to the exact line number and the in-line pixel offset within a few microseconds.
  • Smooth-render debounce. Lines outside the viewport whose height is still unknown are estimated at the mean height and refined progressively while the user drags, which eliminates scrollbar jumping and jitter entirely.

The height tree is what makes virtualised scrolling feel continuous: unknown heights are an estimate that converges, never a blocking full measurement.

2.8 Storage Durability: SaveTicket, Atomic Writes, Disaster Recovery

Saving is triggered by Cmd+S or by an automatic timed save, and every request passes through an ordering lock before it is allowed to touch the file. 

flowchart TD
            Trigger["Save triggered (Cmd+S / automatic timed save)"]
            Ticket["Allocate an increasing SaveTicket (seq = N)"]
            Queue["Enter the file-specific concurrent queue"]
            Check{"While holding the lock: latest_sequence == N ?"}
            Discard["Discard the superseded task (never let an old write clobber newer content)"]
            Tmp["1. Create a .tmp.UUID temporary file in the same directory"]
            Write["2. Write the full payload and compute CRC32"]
            Fsync["3. Call the OS-level sync_all / fsync to force physical sectors to disk"]
            Replace["4. Atomic replace (POSIX rename / Windows MoveFileEx)"]
            History["5. LocalHistoryStore records a rolling version (at most 100)"]

            Trigger --> Ticket
            Ticket --> Queue
            Queue --> Check
            Check -->|No: a newer save task already exists| Discard
            Check -->|Yes: writing is permitted| Tmp
            Tmp --> Write
            Write --> Fsync
            Fsync --> Replace
            Replace --> History

The ordering lock

  1. A monotonically increasing SaveTicket is allocated with seq = N.
  2. The task enters the file-specific concurrent queue.
  3. While the lock is held, the guard validates latest_sequence == N. If it does not match, a newer save task already exists and the superseded task is discarded automatically, which guarantees that an old write never clobbers newer content.
  4. If it matches, the write proceeds through the five atomic steps below.

Atomic write sequence

  1. A .tmp.UUID temporary file is created in the same directory.
  2. The complete payload is written and its CRC32 is computed.
  3. The OS-level sync_all / fsync is called to force the data onto physical sectors.
  4. The destination is replaced atomically (POSIX rename / Windows MoveFileEx).
  5. LocalHistoryStore records a rolling version, at most 100 of them.

RecoveryJournal recovery log

Every edit streams a lightweight journal entry with a CRC32 checksum appended. Even after a power loss, the next launch verifies the journal automatically and replays it to recover within seconds.

LocalHistoryStore local time machine

This relies on Git in no way at all. Each save records a snapshot version in a local database, and the built-in Myers diff algorithm provides character-level insertion and deletion comparison, so any version can be restored with a single click.

WARNING

Durability depends on the ordering lock being honoured: bypassing the ticket check is exactly how a stale write would silently overwrite newer content on disk.
